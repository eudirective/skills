# Consultation controlled-release host test plan

**Status:** Not performed. This plan is for a future host that offers a supported pre-output validation hook. The current skills-only ChatGPT plugin has no such hook, so it cannot run this test or block ordinary hosted responses.

## Preconditions

- Use a test deployment with an explicit, supported callback between answer preparation and user-visible output.
- Install the exact candidate package and record its plugin/core versions and commit.
- Use only fictional or abstract, non-identifying consultation artifacts. Do not use applicant narratives, names, case numbers, precise dates, or dossier documents.
- Capture the host's validation decision and output-channel result without retaining sensitive conversation content.

## Scenarios

### 1. Qualified partial answer passes

Prepare a valid schema 0.4.0 receipt with declared open source or attack-review work, a matching full dashboard, and a qualified partial answer.

**Pass:** the host invokes `controlled-release`, validates the exact receipt and answer bytes, and displays those exact bytes, including the dashboard and open work. The result must not be described as comprehensive.

### 2. Comprehensive claim with open work is withheld

Use a receipt labelled comprehensive while leaving a required C27 check, owner-specific source obligation, attack topic, or review gate open.

**Pass:** the host displays no answer bytes from the candidate and records a blocked result. It must not convert the failed claim to a successful comprehensive answer without producing a newly validated, qualified artifact.

### 3. Answer or receipt changes after validation

Change the answer or receipt between validation and the host's output step, including a race between file read and release where the host architecture allows it.

**Pass:** the host rechecks the exact bytes and emits nothing when a digest or validation record no longer matches.

### 4. Legacy receipt and unsupported invocation

Attempt strict release with a 0.3.0 receipt, a missing dashboard, or a missing validator result.

**Pass:** the host blocks output and records the specific validation failure.

### 5. Alternate output path and bypass check

Attempt to send the answer through every other enabled response, tool, streaming, retry, fallback, and error path.

**Pass:** no user-visible answer can bypass the validator. Any accessible bypass means the host does not provide a non-bypassable release gate.

### 6. Privacy boundary

Inspect all receipt, research, preflight, logging, retry and error artifacts generated by the synthetic scenarios.

**Pass:** only generalized, non-identifying material is persisted or transmitted; failure logs do not copy free-text artifacts unnecessarily. This is a deployment review and does not establish that arbitrary personal data can be detected automatically.

## Evidence to record

- Host and package versions, deployment configuration, and test date.
- For each scenario: input fixture ID, validation outcome, whether any output bytes reached the user-visible channel, and relevant non-sensitive logs.
- Whether all alternative and failure paths were exercised.
- Any bypass, race, privacy issue, or unsupported feature as a release blocker.

Passing a local script test is not a substitute for these observations. A successful test establishes behavior only for the tested host configuration and paths; it does not establish legal correctness or that every material issue was identified.
